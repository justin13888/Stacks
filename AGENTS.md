# stacks — agent guide

Self-hosted media tracker for movies, shows, anime and Asian dramas. Users
sign in through OpenID Connect, browse cameo-indexed metadata (TMDB +
AniList, with a catalog snapshot in PostgreSQL as the fallback), and keep a
lossless library of entries, watch runs and plays. The HTTP surface is a
kynos-built JSON REST API under `/api/v1` whose OpenAPI 3.1 document is
derived from the router itself and committed as `web/openapi.json`; the
reference web client is a Bun + Vite + React 19 SPA driven by a TanStack
Router/Query stack with an orval-generated typed client.

## Tech stack

- **API:** Rust 2024, `cargo` workspace. [kynos](https://github.com/getkono/kynos)
  0.4 (`openapi31`, never `openapi32`): typed guards, typed state, RFC 9457
  problems, and the document derived from the handlers' types
  ([ADR 0003](docs/adr/0003-kynos-http-api.md)). Async via `tokio` (full).
  Logs via `tracing` + `tracing-subscriber` (JSON); metrics via `metrics` +
  `metrics-exporter-prometheus`, labelled by operation id
  ([ADR 0005](docs/adr/0005-observability.md)).
- **Database:** PostgreSQL >= 18, SeaORM 2 (`sqlx-postgres`,
  `runtime-tokio-rustls`). One baseline migration in `core/migration`, run at
  API startup.
- **Auth:** `openidconnect` (authorization code + PKCE, full id_token
  verification), opaque server-side sessions in an httpOnly cookie, and
  scoped `stk_` API tokens stored as SHA-256
  ([ADR 0004](docs/adr/0004-auth-sessions.md)). `hmac` + `sha2` sign
  outbound notification webhooks.
- **Metadata SDK:** [cameo](https://github.com/justin13888/cameo) 0.2 from
  crates.io, `default-features = false, features = ["tmdb", "anilist"]`.
  The `cache` feature is intentionally off — `rusqlite`'s `libsqlite3-sys`
  collides with the copy `sqlx` pulls in via SeaORM. Leave it disabled.
  Only `core/src/media/provider.rs` (the `CameoProvider` adapter) and
  `mapping.rs` may name `cameo::` types; everything else calls the
  `MetadataProvider` trait, whose errors are classified `MetadataError`s.
  `core/tests/metadata_fault_injection.rs` enforces both rules.
- **Web:** Bun (package manager and scripts) + Vite 8 + React 19,
  TypeScript 7, TanStack Router + Query, Tailwind 4 design tokens, Radix
  primitives (`radix-ui`), `motion`, `@dnd-kit`, `recharts`. Tests are
  Vitest + Testing Library under jsdom. The typed client is generated by
  orval 8 from the committed `web/openapi.json`, so the web build needs no
  Rust toolchain; only its hooks talk to the API (the mutator
  `web/src/lib/api-client.ts` is the one `fetch`, enforced by biome and
  `web/src/app.test.ts`). See `docs/adr/0007-web-stack.md`.
- **E2E:** `tests/e2e`, a crate whose library is a Rust client
  [spargen](https://github.com/getkono/spargen) 0.5 generates from
  `web/openapi.json` at build time; its journeys drive a real server.
- **Tooling:** `just` for the task runner, `lefthook` for git hooks, `biome`
  for web formatting / linting, `cargo-llvm-cov` for coverage (ratchet
  thresholds in the `coverage-*` recipes), an exact toolchain in
  `rust-toolchain.toml`.
- **No CLI.** Earlier scaffolding had one; it was dropped. Operator surface
  is the admin API.

## Key conventions

- **Canonical media id.** Every `cameo_media_id` column stores a self-describing
  `<provider>:<kind>:<numeric>` string — e.g. `tmdb:movie:550`,
  `anilist:tv:21`. Episode ids extend with `:<season>:<episode>`. cameo's
  `provider_id` only carries provider + numeric; the kind is folded in at
  Stacks's edge because cameo routes movies and TV through separate calls.
  Parse with `MediaId::parse` / `EpisodeId::parse`; build with `from_cameo`
  + a known `MediaKind`. See [`core/src/media/id.rs`](core/src/media/id.rs).
- **Opaque cursor pagination.** Every collection answers `Page<T> { items,
  next_cursor }` and takes `?cursor=…&limit=…` (default 50, cap 200). A
  cursor is base64url over a keyset position (a UUIDv7 id, a sort key and
  id, or a provider page number for catalog listings); a cursor the server
  did not issue is a 400 `invalid-cursor`, never a silent first page. See
  [`api/src/page.rs`](api/src/page.rs).
- **`JobContext`** carries the `DatabaseConnection` and the shared
  `Arc<dyn MetadataProvider>` into every background job handler.
- **Errors at the API edge.** Every error is an RFC 9457 problem
  (`application/problem+json`). Each operation names its own
  `#[derive(ApiError)]` type, so its declared responses are exactly what it
  can send; shared failures (`Internal`, `TitleNotFound`, `Upstream`,
  `InvalidCursor`) are held with `#[problem(transparent)]`. `Internal` logs
  its cause and answers a fixed body. Problem types are
  `problem::BASE` + slug, documented in
  [ADR 0006](docs/adr/0006-error-model.md).
- **OpenAPI is the router.** Handlers are `#[kynos::get("/path",
  operation_id = "camelCase")]` functions whose first doc line is the
  summary; their extractors, return type and error type are the
  description. `gen-openapi` writes the 3.1 document to `web/openapi.json`
  (committed; `just check-openapi` fails on drift). Nothing ever edits the
  document by hand or post-processes it.
- **Auth.** OIDC only, ending in an opaque session cookie; scripts use
  scoped API tokens. A guard is the handler's first argument: `Reader`
  (session, or token with `read`), `Writer` (`write`), `Administrator`
  (an admin's session, or an admin's token with `admin`), `SessionOnly`
  (credential management). `api/tests/scopes.rs` checks every operation.

## Commits & merging

Every commit is a structured [Conventional Commit](https://www.conventionalcommits.org/),
because `CHANGELOG.md` and the version number are generated from them.
`just commit-lint` is the rule (convco, configured by [`.versionrc`](.versionrc));
the `commit-msg` hook runs it on every commit, and CI runs it on the PR title
and on every commit in the PR (`just commit-lint-range BASE HEAD`).

- **Format.** `type(scope)!: subject`, then an optional body and footers,
  each separated by a blank line.
- **Types.** `feat`, `fix`, `perf`, `refactor`, `revert`, `docs`, `build`,
  `ci` appear in the changelog; `chore`, `test`, `style` are hidden. Nothing
  else is accepted.
- **Scopes.** Optional; when present, one of `api`, `core`, `web`, `ci`,
  `deps`, `docs`.
- **Subject.** Imperative mood ("add", not "added"), lower-case, no trailing
  period, and the whole header at most 72 characters.
- **Breaking changes.** Add `!` after the type/scope (`feat(api)!: drop
  salvo`) whenever a change breaks the HTTP API, the config/env surface, the
  database or backup format, or the deployment, and explain the migration
  in a `BREAKING CHANGE: …` footer. Either one marks the change breaking;
  before 1.0 a breaking change bumps the minor version.
- **The PR title is the commit.** Every merge into `master` is a squash
  merge whose commit title is the PR title, so the PR title must pass
  `just commit-lint` (CI's `pr-title` job checks it, including after edits).
  Commits on the branch are linted too, but only the title reaches `master`.
- **History on `master` is linear.** No merge commits, rebase merges,
  force-pushes or direct pushes; everything lands through a squash-merged
  PR. The required check is `ci-ok`, which aggregates every CI job.
- **`CHANGELOG.md` is generated.** release-please writes it from the squash
  commits; never edit it by hand. A wrong entry is fixed by fixing the
  commit title convention, not the file.
- **Releasing.** release-please keeps a release PR (`chore: release X.Y.Z`)
  open and up to date with every merge. Merging that PR is the release: it
  tags the squash commit `vX.Y.Z`, publishes the GitHub Release, and the
  [release workflow](.github/workflows/release.yml) pushes the GHCR images
  and release assets. The version lives in `[workspace.package]` in the root
  `Cargo.toml` and in `web/package.json`; release-please bumps both. After
  v0.1.0 ships, delete `"release-as": "0.1.0"` from
  `release-please-config.json` so later versions follow the commits.
- **Signing.** No personal GPG/SSH signing keys, PATs or signing secrets are
  used anywhere. GitHub signs the squash commits on `master`, and the
  release workflow (`GITHUB_TOKEN` only) attests every image and release
  asset with `actions/attest-build-provenance`. Tags are not signed: see
  [ADR 0001](docs/adr/0001-release-signing.md).

## Build / test

The [`Justfile`](Justfile) is the single source of truth for every command
— CI (`.github/workflows/ci.yml`) and `lefthook.yml` both call into the
same recipes. Run `just --list` to see them all; don't inline cargo / bun /
biome commands in hooks, CI, or new docs — add or extend a recipe instead.

```bash
just check      # full gate: format-check + lint + typecheck + test + contract + check-openapi (mirrors CI / pre-push)
just lint       # clippy -D warnings + biome lint (read-only)
just format     # write cargo fmt + biome format fixes
just lint-fix   # apply clippy --fix + biome lint --fix
just test       # cargo test (api + core + e2e; DB tests need DATABASE_URL) + Vitest (web)
just commit-lint MSG_FILE          # one commit message (needs convco)
just commit-lint-range BASE HEAD   # every commit in BASE..HEAD
just coverage   # cargo llvm-cov with the ratchet thresholds
just gen-openapi   # rewrite the committed web/openapi.json from the router
just check-openapi # fail when web/openapi.json is stale
just codegen    # orval client + route tree from web/openapi.json (no Rust needed)

just dev-up     # local Postgres (compose.dependencies.yaml)
just dev-api    # cargo run -p stacks-api (needs env)
just dev-web    # vite dev server
```

Per-package shortcuts (`format-api`, `lint-core`, `test-web`, …) exist in
the [Justfile](Justfile) for tighter loops.

## Where to start

### Adding a new API endpoint

1. **Domain logic in `core/`.** Add or extend a service in the relevant
   module (`core/src/<area>/service.rs`); keep repo functions thin (SeaORM
   queries only) and mutations transactional.
2. **Migration (if schema changes).** The baseline is append-only once
   v0.1.0 ships: add a new migration under `core/migration/src/` and register
   it in `lib.rs`. Migrations auto-run on API startup.
3. **DTOs and errors.** In `api/src/<area>.rs`, DTOs derive `Schema` +
   `Serialize` + `Deserialize` (`QueryParams` / `PathParams` /
   `HeaderParams` for parameters); the operation's error is a
   `#[derive(Debug, thiserror::Error, ApiError)]` enum with
   `#[problem(base = crate::problem::BASE)]`, declaring exactly the statuses
   the operation can send. Add each new problem slug to ADR 0006.
4. **Handler.** `#[kynos::get("/path", operation_id = "camelCase")]` with a
   one-line doc summary; the guard first (`Reader`, `Writer`, …), then
   `Path`/`Query`/`Inject<…>` extractors, the body last; return
   `Result<Json<T>, YourError>`. No `unwrap`/`expect` (clippy denies them).
5. **Wire it up.** Mount it in the area's `group()`; a new area adds its
   `pub mod` in `api/src/lib.rs` and its `.group(…)` in
   [`api/src/app.rs`](api/src/app.rs)'s `/api/v1` router.
6. **Test it.** The area's suite in `api/tests/<area>.rs` drives every
   declared response (the generic `support::sweep::sweep` covers the shared
   ones) and ends with `env.assert_covered("<tag>")`; every client calls
   `assert_conformance()`.
7. **Regenerate the document.** `just gen-openapi`, and commit
   `web/openapi.json` with the change; `just codegen` refreshes the web
   client from it.

### Adding a new job type

1. Add a variant to `repo::JobType` in
   [`core/src/jobs/repo.rs`](core/src/jobs/repo.rs) with `as_str` / `parse`
   handling.
2. Create `core/src/jobs/handlers/<name>.rs` with a `Payload` struct
   (`Serialize` + `Deserialize`) and an `async fn handle(ctx: &JobContext,
   payload: Payload) -> Result<(), JobError>`.
3. Register it in `core/src/jobs/handlers/mod.rs`.
4. Wire dispatch into the `match job_type { … }` block in
   [`core/src/jobs/runner.rs`](core/src/jobs/runner.rs).
5. Enqueue with `jobs_repo::enqueue_job(db, jobs_repo::build_job(JobType::Foo,
   Some(payload), max_attempts))`. The runner picks it up within
   the polling interval (10s by default); failures back off with
   `30s × 2^attempts`, capped at 1h.

### Adding a new notification channel

1. Implement
   [`core/src/notifications/channels/mod.rs::NotificationChannel`](core/src/notifications/channels/mod.rs)
   in a new file under `channels/`. The trait is async and gets the
   rendered notification + the user's per-channel config JSON.
2. Re-export from `channels/mod.rs`.
3. Add a branch in `NotificationService::dispatch`'s `match
   channel.channel_type.as_str()` in
   [`core/src/notifications/service.rs`](core/src/notifications/service.rs).
4. Document the config shape (the existing channels declare a
   `ChannelConfig` struct that `serde_json::from_value`s the stored JSON —
   follow the same pattern).

### Other common edits

- **New env var.** Add to `FileXxx` in
  [`core/src/config/file.rs`](core/src/config/file.rs), then layer it in
  [`core/src/config/env.rs`](core/src/config/env.rs) via `require` /
  `optional` / `optional_u64`. Update the table in the README and
  `docs/DEPLOY.md`.
- **New migration.** `m0NN_*.rs` in `core/migration/src/`; add to
  `Migrator::migrations` in `lib.rs`. They run idempotently on every
  startup via `MigratorTrait::up`.
- **Frontend route / page.** TanStack Router with file-based routing under
  `web/src/router/`. The data hooks live in `web/src/api/` (orval-generated)
  and `web/src/hooks/`.
